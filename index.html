쓰기 증폭(WAF)의 발생 원인과 한계

  • 비대칭적 구조: SSD는 쓰기 단위(Page)와 지우기 단위(Block)의 크기 불일치 현상이 존재합니다.
  • GC 오버헤드: 상이한 업데이트 주기를 가진 데이터가 동일 블록에 혼재될 경우, 잉여 공간 확보를 위해 유효 데이터(Valid Page)를 다른 블록으로 복사(GC)해야 합니다.
  • DWPD와 OP의 트레이드오프: WAF의 증가는 NAND 소모를 가속화합니다. 스펙 상의 DWPD(Drive Writes Per Day)를 보장하기 위해서는 디바이스 내 OP(Over-Provisioning) 비율을 늘려야 하므로 원가가 크게 상승하며, 반대로 OP를 유지할 경우 수명 보증 수치가 현저히 저하됩니다.
근본적 문제 제기: 호스트(OS)는 데이터의 특성(Hot/Cold)을 알고 있지만, SSD 컨트롤러는 이를 알지 못하는 '블랙박스(Black-box)' 구조로 인해 불필요한 데이터 혼재가 계속 발생합니다. 👉 이에 대한 해결책이 필요합니다.

기존 블랙박스 모델의 한계

  • 기존 SSD 컨트롤러는 호스트 워크로드의 의도나 수명을 인지하지 못한 채, 가용 블록에 데이터를 임의로 배치합니다.
  • 이에 따라 런타임 중 데이터 혼재 현상이 필연적으로 발생하며, WAF 및 Latency Spike를 유발합니다.

FDP의 핵심 원리

  • 호스트(OS/App)가 I/O 요청 시 데이터 수명 특성을 나타내는 Placement Identifier (PID)를 함께 전달합니다.
  • 디바이스는 수신된 PID를 기준으로 데이터를 별도의 물리적 블록 집합에 격리 저장하여, 블록 단위의 데이터 생명 주기를 동기화하고 GC를 최소화합니다.

1. Reclaim Group (RG)

플래시 미디어 내에서 독립적으로 GC가 수행되는 영역입니다. 다중 RG 간에는 미디어 레벨의 병렬성을 확보할 수 있습니다.

2. Reclaim Unit (RU)

FDP에서 관리하는 최소 스토리지 할당 단위로, 내부적으로 다수의 NAND Block들로 구성되어 실제 Erase 작업이 일어나는 단위입니다.

3. Reclaim Unit Handle (RUH)

SSD 컨트롤러가 현재 데이터를 기록하기 위해 열어둔(Open) 활성 RU를 지칭하는 내부 포인터 리소스입니다.

4. Write Stream

호스트가 데이터 생명 주기 격리를 위해 각 I/O 단위에 부여하는 식별자이며, 디바이스 내의 특정 RUH로 매핑됩니다.

Related Work: 기존 FDP 도입 방식의 구조적 한계 및 실증 사례

애플리케이션 및 파일시스템 계층 기반 제어의 문제점

1. Application-Driven 모델

  • 사례: CacheLib 등 (io_uring passthrough 사용)
  • 엔지니어링 비용: 상용 애플리케이션의 I/O 엔진(소스코드) 직접 수정 필요.
  • 컨텍스트 유실: Buffered I/O 및 Writeback 경로를 지원하지 못해 범용성 한계.

2. FS-Driven 모델

  • 사례: FStream (파일 속성 기반), F2FS (세그먼트 온도 기반)
  • 휴리스틱 예측의 불확실성: 파일 속성만으로는 실제 런타임 생명 주기를 정확히 추론하기 어려움.
  • 데이터 편향 (WARP 연구): F2FS에 제어를 일임한 결과, 전체 데이터의 99%가 단일 WARM RUH로 집중되어 스트림 분리 효과가 상실됨.

3. Kernel-Driven 모델 (LBA / Program Context 기반)

  • 사례: AutoStream (LBA 패턴 추론), PCStream (Issuing Program Context 기반)
  • 운영자(Operator) 제어 불가: 시스템 관리자가 텐넌트나 워크로드의 특성을 알고 있어도, 커널이 자동으로 추론하므로 명시적인 정책 개입 및 제어가 불가능함 (Operator intent 반영 불가).
  • 한계점: 애플리케이션 수정은 피했으나, 커널 내에서 지속적인 모니터링 연산 및 그룹 재구성 비용(Overhead) 발생. io.stream은 cgroup이 이미 제공하는 그룹화 정보와 운영자의 명시적 제어를 통해 이를 해결함.

왜 Container (cgroup)가 이상적인 FDP 제어 단위인가?

효율적인 데이터 격리를 위한 최적의 Granularity

본 논문은 데이터센터 환경에서 컨테이너(cgroup) 단위가 데이터 수명 주기를 그룹화하고 FDP 스트림을 할당하기 위한 가장 이상적이고 실용적인 Granularity임을 제안합니다.

1. 모든 I/O Path에 내장된 컨텍스트

cgroup (blkcg) 식별자는 VFS부터 Page Cache, Block Layer에 이르기까지 모든 I/O 경로에 기본적으로 태깅되어 유지됩니다. 따라서 애플리케이션의 수정 없이도 정확한 I/O 출처 추적과 스트림 맵핑이 자연스럽게 이루어집니다.

2. 운영자(Operator) 친화적 관리 단위

데이터센터와 클라우드 환경의 시스템 운영자(Operator)는 이미 쿠버네티스(Kubernetes) 등 오케스트레이터를 통해 컨테이너(cgroup) 단위로 자원을 격리하고 관리하고 있습니다. 따라서 이를 FDP 스토리지 격리 기준으로 활용하는 것은 기존의 인프라 관리 체계와 완벽하게 부합합니다.

범용적 I/O 경로 지원 및 동작 시퀀스

  1. 다양한 I/O 경로 지원: 애플리케이션은 Buffered I/O(Page Cache 경유), Direct I/O(FS 직접 접근), 혹은 FS를 우회하는 Raw Device 접근 중 어떤 방식을 사용하더라도 io.stream의 데이터 격리 혜택을 받습니다.
  2. 컨텍스트 유지 (Buffered I/O): 비동기 Writeback 동작 시, 커널은 해당 Page를 더럽힌(Dirty) 원본 blkcg 컨텍스트를 정확히 역추적하여 Block Layer에 인가합니다.
  3. 컨텍스트 획득 (Direct I/O & Raw): I/O를 발행하는 현재 프로세스 컨텍스트에서 즉시 blkcg를 획득하여 Block Layer로 전달합니다.
  4. PID 변환 및 투명성: 상위의 어떤 경로를 거치든 모든 I/O는 Block Layer로 수렴합니다. 이곳에서 NVMe 커맨드 생성 시 cgroup ID를 디바이스 스트림 ID(RUH)로 매핑하므로 완벽한 호환성이 보장됩니다.

할당 정책(Policies) 및 시나리오 동작

  • 명시적 할당 (Explicit Policy): cgroup v2의 io.stream 속성 노드에 스트림 ID를 기록하면, 해당 테넌트에서 발생하는 모든 I/O는 지정된 RUH로 확정 매핑됩니다.
    echo "259:0 1" > /sys/fs/cgroup/Tenant_A/io.stream
  • I/O Hint 우선 (Bypass): 같은 cgroup에서 발생한 I/O라도, 이미 Stream ID가 명시적으로 지정된 I/O의 경우 cgroup 정책에 의해 덮어씌워지지 않고 기존 Stream ID를 유지합니다.
  • 기본 정책 (Default Fallback): 명시적으로 io.stream이 설정되지 않은 프로세스나 최상위 Root cgroup의 I/O는 모두 시스템 기본 스트림(RUH 0)으로 수렴합니다.
  • 🌟 메타데이터 자동 격리 (Free Metadata Isolation):
    ext4의 jbd2 저널링과 같은 메타데이터 쓰기는 기본 Root 컨텍스트로 처리되어 별도 튜닝 없이 사용자 데이터와 격리되는 부수적 효과(Free)를 얻습니다. 하지만 실험 결과(Metadata-only WAF 1.53), 메타데이터 격리만으로는 WAF 개선 효과가 미미하며, 이득의 핵심 원천은 사용자 데이터의 철저한 수명 기반 격리입니다.

하드웨어 제원 및 5종의 대조군(Baselines) 정의

시스템 및 하드웨어 스펙

  • CPU / Memory: Intel Core i9-12900K / 64GB RAM
  • 운영체제: Linux Kernel 7.0 (io.stream 패치 적용)
  • 스토리지 하드웨어: Samsung PM9D3a 4TB Datacenter FDP NVMe SSD
  • 제약 사항: OP(Over-Provisioning) 7%, 총 RUH 8개 (메타데이터용 1개 + 데이터용 7개)
  • 평가 기준점 (Ideal WAF): 쓰기 증폭의 이론적 하한선은 1.00입니다.

평가 대조군(Baselines) 5종

  • 1. No-FDP: 기존 일반 블록 디바이스 (FDP 비활성화)
  • 2. FDP-default: FDP는 켰으나, 모든 I/O를 1개의 기본 스트림(RUH 0)에 던지는 상태
  • 3. Oblivious: 가용 스트림 7개를 14개 그룹에 규칙 없이 무작정 쏟아붓는 정책 부재 상태
  • 4. Blind: 2개 스트림에 데이터를 묶긴 묶었으나, 수명을 무시하고 임의(Random)로 매핑한 상태
  • 5. Coherent (io.stream): 테넌트별/수명별 명시적 정책에 따라 스트림을 정확히 분배한 이상적 상태
💡 교훈: 모든 평가는 1.0(Ideal)과 다양한 실패 시나리오(Blind, Oblivious) 사이의 위치를 확인하는 과정입니다.

Q1. "FDP만 켜면 되는 거 아냐?"

하드웨어 기능 활성화(FDP-default)와 파일시스템 튜닝의 실제 한계

하드웨어만 믿었을 때의 처참한 결과

  • Raw Device (Filesystem 없음):
    No-FDP 1.65  →  FDP-default 1.65 (차이 없음)
  • ext4 적용 시:
    No-FDP 1.50  →  FDP-default 1.53 (오히려 나빠짐)
  • xfs 적용 시:
    No-FDP 1.57  →  FDP-default 1.61 (오히려 나빠짐)
  • Metadata-only 분리:
    FS 메타데이터만 떼어내도 WAF는 1.53에 머뭄. 메타데이터 분리가 마법의 탄환이 아님.
  • io.stream (Coherent): WAF 1.00 (수명 기반 격리 달성)
💡 교훈: FDP는 켜는 게 아니라 "쓰는 것"이다. 베이스라인(No-FDP) 선택과 분석이 논문의 절반이다.

Q2. "그럼 스트림 많이 주면 되겠네?"

스트림 프로비저닝 규모보다 '분배 정확도(Policy)'가 절대적인 이유

정책 없는 자원 할당의 재앙

  • Oblivious (무작위 분산): 14개 cgroup에 7개 스트림 전량을 규칙 없이 매핑.
    WAF 2.36 폭주. 스트림 1개짜리 FDP-default(1.62)보다 훨씬 나쁨.
  • Blind (잘못된 분배): 수명을 무시하고 임의로 2개 스트림에 묶음.
    WAF 1.30. 성능을 깎아먹는 나쁜 매핑.
  • Fallback (우아한 저하): 스트림이 모자라서 여러 cgroup이 하나의 기본 스트림(RUH 0)으로 떨어질 때.
    WAF 1.07 방어. 모자라도 시스템이 붕괴하지 않음을 증명.
  • Coherent (정합성): 수명에 맞춰 정확히 매핑 (단 2개 스트림만 사용).
    WAF 1.00 달성.
💡 교훈: 자원을 더 준다고 좋아지지 않는다. 스트림 개수가 아니라 "매핑"이 변수다.

왜 스트림을 아껴 써야 하는가? (OP Constraint)

스트림 낭비가 펌웨어 내부 가용 자원(Effective OP)에 미치는 치명적 영향

1. No-FDP (글로벌 풀)

Effective OP: 최대 (Max) 데이터 격리: 수행 불가

전체 Free Block을 단일 풀로 운용하여 디바이스 내 OP 비율이 극대화되나, 서로 다른 수명의 I/O가 섞여 필연적으로 WAF가 상승합니다.

2. FDP (적절한 스트림 수)

Effective OP: 안정적 확보 데이터 격리: 완벽 격리

소수의 스트림(예: 2개)만 사용하여 수명이 비슷한 데이터끼리 묶으면(Coherent), 여유로운 Free Block(OP)을 유지하면서도 완벽한 격리가 가능합니다.

3. FDP (스트림 과다 사용)

Effective OP: 고갈 (Starvation) 데이터 격리: 성능 붕괴

각 스트림(RUH)은 독립된 활성 블록(Open Block)과 개별 GC 풀을 요구합니다. 많은 스트림을 열수록 펌웨어 내 통합 가용 OP가 조각나고 급감하여 시스템이 마비됩니다.

💡 교훈: SSD의 빈 공간(OP) 제약 때문에 스트림은 "무조건 적게" 써야 한다. (그룹핑 필수)

Q3. "진짜 워크로드에서도 통할까?"

4종 상용 애플리케이션 12시간 구동: 앱별 할당 vs 수명별 묶음 할당

수명 기반 그룹핑(Grouping)의 실효성 증명

  • 기본 정책의 실패:
    FDP-default 1.70 / 1-stream 1.70 (단일 스트림으로는 개선 불가)
  • Per-App 매핑 (낭비적 이상향):
    4개 앱 각각에 4개의 전용 스트림 할당  →  WAF 1.23
  • Lifetime 매핑 (io.stream 제안):
    수명이 비슷한 앱끼리 묶어 2~3개 스트림만 사용  →  WAF 1.27 (거의 유사함!)
  • Mixed 매핑 (잘못된 묶음): 수명이 다른 앱들을 강제로 섞음.
    WAF 1.58 / 1.80 폭주. 묶는 "기준"이 틀리면 재앙이 됨.
💡 교훈: 앱마다 스트림을 낭비할 필요 없다. "수명이 비슷하면 묶어도" 동등한 효과를 낸다.

안 되는 것 / 아직 모르는 것 (Limitations & Open Questions)

본 논문의 한계점과 추후 연구가 필요한 미해결 과제들
  • cgroup 경계 ≠ 데이터 Lifetime:
    단일 컨테이너(cgroup) 안에도 수명이 천차만별인 데이터가 혼재합니다. (예: RocksDB 내의 수명이 짧은 WAL과 긴 SSTable, Temp). io.stream의 매크로(Macro) 제어만으로는 애플리케이션 내부의 미세한 수명 차이를 찢어낼 수 없습니다.
  • 방향 비대칭 현상의 원인 미규명:
    잘못된 매핑 시 한쪽 방향(1.07)은 방어되나 반대 방향(3.43)은 심각하게 붕괴하는 현상이 발견되었으나, 펌웨어 내부 동작을 볼 수 없어 정확한 원인은 밝혀내지 못했습니다.
  • Tail Latency (p99) 개선의 근본 원인:
    p99 지연시간이 93%나 개선되었으나, 이는 블랙박스 내의 관측(Observation) 결과일 뿐입니다. 정확히 어떤 FTL 큐가 해소되었는지는 아직 가설 단계에 머물러 있습니다.
  • 실험 시간의 제약:
    12시간의 상용 워크로드 평가는 유의미하지만, 수년에 달하는 SSD의 전체 라이프사이클 마모도를 대변하기엔 상대적으로 짧은 시간입니다.

결론 (Conclusion)

Host-Managed Storage 패러다임의 실효적 구현 및 향후 지향점

주요 연구 성과 및 의의

  • Zero-Modification 호환성: 레거시 워크로드 및 범용 파일시스템 스택의 코드 변형을 배제하여 NVMe FDP 기술의 실무 진입 장벽을 완전히 허물었습니다.
  • Operator-Driven 아키텍처: 시스템 운영자 관점의 매크로(Macro) 자원 경계를 물리 매체(NAND)까지 1:1로 전달하는 효율적 아키텍처를 제시했습니다.
  • 정책적 교훈 도출: "FDP는 하드웨어가 아니라 정책이다." 올바른 매핑 없이 스트림 자원만 늘리는 것은 오히려 성능을 파괴함을 실증했습니다.
